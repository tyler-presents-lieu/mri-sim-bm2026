# MRI Simulator Implementation Plan

## 1. Purpose and audience

This application is an interactive, presentation-oriented explanation of basic MRI concepts for a non-technical audience. It must favor clear, visible cause-and-effect over physical completeness. The experience progresses through small, increasingly rich demonstrations while preserving controls that let the presenter answer questions live.

The first deliverable is a browser application served locally by Python and managed with PDM. During development it must run through a GitHub Codespaces forwarded port, so it can be used from a Chromebook browser. It should also run locally without network access after dependencies have been installed.

## 2. Product goals

### Primary goals

- Make spin alignment, precession, resonance, gradients, dephasing, and the connection to measured signal visible.
- Provide a sequence of named presentation scenes that can be selected directly or advanced linearly.
- Keep each scene interactive through compact controls for fields, gradients, RF pulses, animation, and reset.
- Use deliberately simplified, stable physics with units shown consistently.
- Run smoothly for grids from one spin through $20 \times 20$ spins at 60 FPS on ordinary laptops.

### Non-goals for version 1

- Diagnostic-quality MRI physics or tissue modeling.
- Slice selection, full pulse-sequence design, reconstruction of real scanner data, or 3D rendering.
- Hardware integration, user accounts, or a multi-user presentation.

A later static deployment is optional, but it is not needed for the presentation use case.

## 5. Simulation model

### Coordinate and state conventions

Represent each hydrogen ensemble as one visual spin rather than a literal atom. A spin at grid position $(x, y)$ has a normalized magnetization vector:

$$
\mathbf{M} = (M_x, M_y, M_z)
$$

where $M_z$ is longitudinal magnetization (aligned to the main field) and $(M_x, M_y)$ is transverse magnetization. Store an $N \times 3$ NumPy array for all spins, plus immutable position coordinates and a per-spin angular frequency.

Use display units of Hz for frequency, seconds for time, and arbitrary normalized magnetization units. The default center frequency is $f_0 = 0.1$ Hz, therefore:

$$
\omega_0 = 2\pi f_0
$$

This intentionally slow baseline lets viewers perceive precession without time scaling. Provide a simulation-speed multiplier for live explanation.

### Field and gradient model

Use a normalized main field $B_0$ solely as an alignment-strength control and frequency source. Do not expose real tesla units in version 1. Frequency at each spin is:

$$
f(x,y) = f_0 + G_x x + G_y y
$$

where $G_x$ and $G_y$ are configured in Hz per normalized grid unit. Center all grid coordinates at zero and normalize extents to $[-1, 1]$. This makes gradient settings independent of grid resolution.

For the prescribed gentle $x$ gradient demonstration, choose:

$$
G_x = 1/6\ \mathrm{Hz}
$$

so spins at $x=-1$ and $x=1$ differ by $1/3$ Hz and accumulate a full $2\pi$ relative phase difference in three seconds.

### Free precession

Each simulation step rotates transverse magnetization around $z$ by:

$$
\Delta\phi_i = 2\pi f_i \Delta t
$$

Apply the rotation directly to each spin's $(M_x, M_y)$ components. Keep this analytic update rather than numerically integrating the Bloch equation; it is more stable and is sufficient for the teaching goal.

### Relaxation

Model relaxation as exponential return to equilibrium:

$$
M_z(t+\Delta t) = 1 - (1-M_z(t))e^{-\Delta t/T_1}
$$

$$
M_x,M_y(t+\Delta t) = M_x,M_y(t)e^{-\Delta t/T_2}
$$

Default $T_1 = 8$ s and $T_2 = 4$ s. These are presentation-friendly values, not a claim about a specific tissue. Scene defaults may disable relaxation when it would obscure the concept.

### Alignment and randomness

**Slide 1 priority: visible field-alignment behavior.** At zero field, draw each spin with a changing random orientation but do not claim it is a molecular simulation. When $B_0$ ramps on over approximately one second, the visual state must clearly show all spins aligning toward the $+z$ direction (pointing upward). This is the primary teaching moment: random thermal jitter → field-imposed order. The physical spin model can begin at a small randomized vector and settle through the same $T_1$ equation; render-only jitter combined with a clear alignment arrow makes the first scene vivid.

After field alignment, spins will precess in the transverse plane with occasional relaxation effects. Later scenes build on this foundation to show frequency selectivity and spatial encoding.

Use a seeded `numpy.random.Generator` per scene reset. The initial state is repeatable for tests and recordings, while the seed can be changed from a hidden developer setting if desired.

## 6. RF pulse model

An RF pulse is a finite-duration command with fields:

```python
@dataclass(frozen=True)
class RFPulse:
    start_s: float
    duration_s: float
    frequency_hz: float
    flip_angle_rad: float
    phase_rad: float = 0.0
```

During a pulse, calculate detuning for spin $i$ as $\Delta f_i = f_i - f_\mathrm{RF}$. Apply a frequency-selective flip around a transverse axis whose strength falls off smoothly with detuning:

$$
a_i = \mathrm{sinc}(\pi \Delta f_i\tau)
$$

Then rotate $\mathbf{M}_i$ by $a_i\theta$ around the pulse phase axis in the transverse plane. This is intentionally an intuitive approximation: resonant spins receive the full flip, and off-resonant spins barely move. Clamp the result only when needed to protect against floating-point drift.

For the resonance scene, schedule three equal visual pulses with frequencies below, equal to, and above $f_0$. The center pulse should be the resonant one and produce a visible $90^\circ$ flip.

## 7. Signal calculation

The receive signal is the complex sum of transverse magnetization:

$$
S(t) = \sum_i (M_{x,i}(t) + jM_{y,i}(t))
$$

Expose magnitude $|S|$, real part, and imaginary part. Render a short scrolling signal strip with the magnitude selected by default. With no gradient, aligned spins reinforce each other. With gradients, phase spread causes visible cancellation. Maintain a bounded ring buffer of timestamped samples, decimated for display but retaining the model's complete per-frame state only when recording is explicitly enabled.

The later Fourier-transform scene can use the same samples as its input. Version 1 should show the conceptual mapping from spatial phase pattern to signal trace, not implement a full reconstruction workflow.

## 8. Application architecture

### Model layer

`model.py` owns `SpinSystem`, its state arrays, parameters, reset, step, gradient-frequency computation, and aggregate magnetization. It imports NumPy only and has no web-framework dependency.

`pulses.py` owns pulse scheduling and pure functions that apply a pulse to a `SpinSystem`. Pulse history is queryable so the renderer can show current and completed pulses.

`signal.py` owns `SignalBuffer` and functions that turn magnetization into complex receive samples.

### Server and browser layers

`scenes.py` defines a `SceneConfig` for each slide: title, explanatory sentence, spin layout, starting model parameters, enabled controls, optional scheduled pulses, and render mode. Scene changes construct a fresh `SpinSystem` and `SignalBuffer` from this configuration.

`server.py` exposes scene metadata and simulation endpoints. A session owns a `SpinSystem`, scheduled pulses, and a signal buffer. The endpoints are `GET /api/scenes`, `POST /api/session`, `POST /api/session/{id}/command`, and `GET /api/session/{id}/state`. Commands and state payloads use typed Pydantic models.

The TypeScript client owns frame timing and user interaction. `controls.ts` maps mouse and keyboard events to typed commands such as `SetGradient`, `TriggerPulse`, `TogglePause`, `ResetScene`, `SelectScene`, and `SetView` (for 3D/top-down/color-arrow view switching). It sends a command request and renders only server-supplied state, preventing the browser from acquiring an independent physics model.

`rendering.ts` reads state but never mutates it. It provides a pluggable renderer that draws the selected view (3D isometric, top-down, or colored arrows), field arrows, gradient frequency legend, phase-color bar (twilight colormap for $[0, 2\\pi]$ phase), pulse timeline, aggregate signal, and a compact scene title into Canvas. The 3D renderer uses Canvas 2D with perspective math; no WebGL is required.

### Frame loop

1. The browser polls controls and turns input into commands.
2. Commands update the server session immediately (scene selection, reset, pause, parameter changes).
3. The browser requests state at 30 Hz and renders it with `requestAnimationFrame` at display refresh rate.
4. The server advances each running session in fixed increments of $1/120$ s, capped at five increments per state request.
5. The server samples the receive signal once per simulation increment and returns the latest display-ready trace.

Fixed simulation timesteps prevent the explanation from changing when rendering or network requests drop frames. Discard excessive accumulated real time after the cap rather than simulating a large, visually confusing jump. A single local presenter session is the target; the server can expire idle sessions after 30 minutes.

## 9. Presentation scenes

| ID | Concept | Default setup | Presenter controls |
| --- | --- | --- | --- |
| `alignment` | **Field aligns random spins** (primary focus: visible transition) | One spin with random jitter, field initially off | Main field ramp on/off, speed, reset, view toggle |
| `resonance` | RF at natural frequency excites a spin | One aligned spin, three scheduled pulses around $0.1$ Hz | RF frequency, flip angle, replay sequence, pause, view toggle |
| `line_selectivity` | Gradient maps frequency to position | 10 spins in a horizontal line, nonzero $G_x$ | Gradient strength, RF frequency, replay/select pulse, view toggle |
| `uniform_grid` | Coherent precession | $10 \\times 10$ grid, no gradients | Grid size, $B_0$, pause, reset, view toggle |
| `x_dephasing` | A gradient accumulates phase difference | $10 \\times 10$ grid, $G_x=1/6$ Hz | $G_x$, speed, relaxation toggle, reset, view toggle |
| `xy_gradients` | Two-dimensional spatial frequency variation | $10 \\times 10$ grid, independent $G_x$, $G_y$ | Both gradients, grid size, view toggle, phase color |
| `signal_bridge` | Receive signal and Fourier intuition | Same grid with configurable gradients | Both gradients, signal view, play/pause, reset, view toggle |

The scene navigator should be accessible with left/right arrow keys, number keys, and an unobtrusive on-screen step indicator. Scene changes reset simulation time unless an explicit future feature adds a comparison mode.

## 10. Visual design and interaction

### Multi-view rendering strategy

Provide three complementary views to suit different teaching moments and screen sizes:

1. **3D isometric view (StarCraft angle):** Render each spin as a 3D arrow with isometric projection (~30° angle). Vertical height represents $M_z$ (longitudinal), and the horizontal ellipse projection shows the precessing transverse plane. This view best communicates the full 3D nature of alignment and precession, especially in slide 1's field-alignment transition.

2. **Top-down view:** Project from above the $xy$-plane. Spins appear as rotating arrows or phase-colored circles. This view excels at showing spatial frequency patterns and dephasing in gradient scenes; eliminates the 3D perspective when examining 2D gradients.

3. **Colored arrow view:** Simplified overlay showing phase as color (twilight colormap) and intensity as arrow length. Useful for dense grids and phase visualizations without 3D clutter.

ByDefault, the single-spin and resonance scenes use the 3D isometric view. Grid and gradient scenes default to the top-down view. All scenes can switch views with a keyboard shortcut (e.g., `1` for 3D, `2` for top-down, `3` for color arrows).

### Color and styling

- Use a dark neutral background with high-contrast field lines and spins. Reserve red for RF energy, cyan/green for transverse magnetization.
- For phase visualization (especially in gradient dephasing scenes), use the **twilight colormap** from matplotlib: a cyclic blue–magenta–blue scale that naturally maps $[0, 2\pi]$ phase without false feature emphasis at rainbow boundaries.
- In line and grid scenes, show a thin frequency legend and label low/high frequency rather than crowding every spin with a number.
- Keep instructional copy to one plain-language sentence per scene. The presenter narration does the deeper teaching.
- Use sliders for continuous controls, toggles for relaxation and pause, and icon buttons for reset/play. Every control must have a keyboard alternative.
- Provide a `?` overlay with keyboard shortcuts, view-switching keys, and a fullscreen button using the browser Fullscreen API.
- Respect a minimum window size of $1024 \times 720$ and scale the drawing layout proportionally above it. At smaller sizes, preserve the spin view and collapse nonessential labels before reducing text below 14 px.

Keep built-in scene definitions in Python dataclasses in version 1. Add optional JSON scene loading only after the built-in progression is stable; that avoids configuration format work before the teaching model has settled.

## 12. Test strategy

Tests must primarily exercise the deterministic model without opening a GUI:

- A zero-gradient system gives all spins equal frequency.
- The prescribed $G_x=1/6$ Hz gradient creates a $2\pi$ phase difference between endpoint spins in three seconds.
- Free precession preserves transverse magnitude when relaxation is disabled.
- Relaxation moves $M_z$ toward one and decreases transverse magnitude.
- A resonant pulse produces a larger flip than an equally sized off-resonant pulse.
- The aggregate receive signal equals the complex sum of all spin vectors.
- Each `SceneConfig` creates valid positions, supported controls, and expected default gradients.
- A headless smoke test can initialize every scene and advance 120 updates.

Use tolerances appropriate for float64 calculations, usually `pytest.approx(..., abs=1e-9)`. Add FastAPI endpoint tests for session creation, commands, and state serialization. Use Playwright for a headless browser smoke test covering application load, scene navigation, a control change, and a nonblank Canvas at desktop and Chromebook-sized viewports. Test presentation behavior manually through a concise checklist: fullscreen toggle, every scene navigation path, mouse and keyboard controls, 1024x720 layout, and an end-to-end resonance replay.

## 13. Implementation phases

### Phase 1: project foundation

1. Create `pyproject.toml` with PDM, Python 3.12, FastAPI, Uvicorn, NumPy, pytest, and development lint/format tooling.
2. Add the package skeleton, FastAPI entry point, and a TypeScript/Canvas browser shell.
3. Implement `SpinSystem` with reset, field frequencies, fixed-step precession, and aggregate magnetization.
4. Add model tests for precession and gradients.

Acceptance: `pdm run mri-sim` starts a server on port 8000 and its Codespaces-forwarded URL opens an animated one-spin page.

### Phase 2: core teaching primitives

1. Draw one spin as a 3D isometric arrow: vertical height for $M_z$, horizontal ellipse for transverse plane.
2. Implement field ramp/alignment to make the **primary teaching moment** vivid: random thermal jitter → all spins point up with $B_0$ on. Use clear visual cues (arrow pointing upward, gradual alignment over ~1 second).
3. Add zero-field jitter, pause, speed, and reset controls.
4. Implement RF pulses and a timeline indicator.
5. Build the alignment and resonance scenes with replayable three-pulse scheduling.

Acceptance: the alignment scene clearly shows field-induced order, and the center-frequency RF pulse visibly flips the spin much more than its neighbors.

### Phase 3: spatial encoding

1. Add line and grid layouts with normalized coordinates.
2. Implement multi-view rendering: 3D isometric (default for single/resonance scenes), top-down (default for grids), and colored-arrow modes.
3. Add $G_x$ and $G_y$ controls and frequency/phase color mapping using the **twilight colormap** for $[0, 2\\pi]$ phase.
4. Implement `line_selectivity`, `uniform_grid`, `x_dephasing`, and `xy_gradients` scenes with view-toggle controls.
5. Tune the $x$ gradient scene so endpoint phase separation reaches one full cycle in three seconds at 1x speed.

Acceptance: a frequency-selected pulse visibly affects a local portion of the line, gradient dephasing is clear on a $10 \\times 10$ grid, and view toggling works for all scenes.

### Phase 4: signal bridge and presentation polish

1. Add receive-signal calculation, bounded trace buffer, and plot renderer.
2. Build the `signal_bridge` scene and concise explanatory labels.
3. Finish scene navigation, keyboard shortcuts, browser fullscreen, responsive layout, and help overlay.
4. Run manual presentation rehearsal and adjust defaults for clarity.

Acceptance: scenes can be presented linearly without opening developer tools, while all useful live controls remain available.

### Phase 5: release delivery

1. Document prerequisites, PDM commands, Codespaces port forwarding, controls, and offline local use in the README.
2. Add a production client build step served by FastAPI and verify it without the Vite development server.
3. Test the local server workflow on a second computer where practical.

Acceptance: a new user can run `pdm install` then `pdm run mri-sim`, open `http://localhost:8000`, and use the full presentation. In Codespaces, the same port can be opened through the Ports view.

## 15. Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| Physics becomes too detailed to explain | Keep one conceptual simplification per visible behavior and label units as normalized where appropriate. |
| Visuals slow down on older laptops | Vectorize model updates, cap the grid at $20 \times 20$, and use simple Canvas primitives. |
| Presenter gets lost in controls | Scene-specific controls, reset button, keyboard navigation, and stable defaults. |
| Browser/server compatibility issue | Treat the PDM local server as the supported delivery path; test current Chromium and Firefox on desktop plus ChromeOS through Codespaces. |
| Animation frame rate changes results | Use a fixed simulation timestep independent of rendering. |

## 16. Definition of done for version 1

Version 1 is complete when a presenter can run the local web application or its Codespaces preview, advance through all seven scenes, interactively alter fields/gradients/RF settings, and demonstrate the intended resonance and three-second dephasing effects. The model tests, API tests, browser smoke tests, and a manual fullscreen presentation pass must be green before release.
